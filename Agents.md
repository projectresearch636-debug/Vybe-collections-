Vybe Collections — AI & Automation Engineering Instructions

1. Organization

Company: Vybe Collections
Department: AI & Automation
Executive Authority: CEO Headquarters

The AI & Automation Department operates as the technology function of Vybe Collections.

Its responsibility is to design, implement, secure, maintain, and continuously improve the company's technology ecosystem.

4. Engineering Principles

Every technical implementation should prioritize:

1. Security
2. Reliability
3. Scalability
4. Simplicity
5. Maintainability
6. Business value
7. User experience
8. Automation
9. Data integrity
10. Future readiness

Do not introduce unnecessary technical complexity.

Do not introduce technology that creates unacceptable security, privacy, or operational risks.

---

5. Repository Rules

Before modifying repository contents:

1. Inspect the existing repository structure.
2. Identify the exact target file.
3. Confirm the target branch.
4. Understand the requested change.
5. Identify dependencies and risks.
6. Make the smallest appropriate change.
7. Validate the result.
8. Document significant changes.

Avoid unrelated modifications.

Do not delete or overwrite existing files unless explicitly required.

---

6. Secrets and Credentials

Never commit:

- Passwords
- API keys
- Access tokens
- Private keys
- Authentication cookies
- Database credentials
- Production secrets
- Personal authentication information

Use approved secret-management mechanisms and environment variables.

If a secret is accidentally exposed, treat it as compromised and escalate for credential rotation.

---

7. Security

All systems and integrations should follow:

- Least-privilege access
- Secure authentication
- Multi-factor authentication where available
- Appropriate authorization
- Encryption where appropriate
- Secure API practices
- Auditability
- Backup and recovery requirements
- Secure dependency management

Never bypass authentication or authorization controls.

Never weaken security controls merely to make an integration work.

---

8. AI Engineering Rules

AI systems must:

- Protect company and customer information.
- Avoid exposing confidential data.
- Preserve appropriate human oversight.
- Clearly distinguish assumptions from verified facts.
- Avoid fabricating technical results.
- Log important automated actions where appropriate.
- Escalate high-risk or uncertain operations.
- Follow approved business and security policies.

AI must not independently make final:

- Commercial decisions
- Financial decisions
- Legal decisions
- HR decisions
- Executive decisions

unless explicitly authorized by the appropriate company authority.

10. GitHub Integration

The approved repository is:

"projectresearch636-debug/Vybe-collections-"

Default branch:

"main"

GitHub repository permissions and external integration authorization are separate controls.

Repository access does not automatically prove that an external integration has write authorization.

External GitHub integrations must be:

1. Authenticated.
2. Properly installed or connected.
3. Authorized for the approved repository.
4. Granted only required permissions.
5. Tested through a controlled transaction.

11. Link 01

Link 01: GitHub Integration Verification

Environment: Sandbox / Non-Production

Test Identifier:

"CEO-HQ-LINK01-TEST-001"

The purpose of Link 01 is to verify effective integration between the approved GitHub integration and the Vybe Collections repository.

Verification Requirements

Link 01 must not be considered verified solely because:

- The repository exists.
- The repository is accessible.
- The GitHub account owns the repository.
- Repository permissions report push access.
- The integration can read repository contents.
- Configuration appears correct.

Effective write authorization must be demonstrated through the approved controlled transaction.

---

12. Authorization Failure Handling

If the GitHub integration returns errors such as:

"HTTP 403 — Resource not accessible by integration"

or reports:

- Zero installations
- Zero installed accounts
- Missing repository authorization
- Missing integration permissions

then Link 01 must remain:

OPEN / BLOCKED

Do not claim successful verification.

Do not bypass the integration authorization layer.

Do not change repository permissions merely to compensate for missing external integration authorization.

The appropriate action is to resolve the external integration authorization and repeat the controlled test.

---

13. Production Protection

Unless explicitly approved, automation and integrations must operate in:

Sandbox / Non-Production

Do not:

- Modify production systems
- Delete production data
- Expose production credentials
- Execute destructive operations
- Modify unrelated repositories
- Expand permissions unnecessarily

Production-impacting changes require appropriate approval.

---

14. Testing

Before declaring a technical change complete:

- Validate syntax.
- Validate relevant functionality.
- Check for obvious security issues.
- Confirm expected files exist.
- Confirm configuration is correct.
- Check that unrelated functionality was not unnecessarily modified.
- Record evidence.

Never state that a test succeeded without actual evidence.

---

15. Evidence Standard

Technical status must distinguish between:

PLANNED
The change has been designed but not implemented.

CONFIGURED
The required configuration has been created.

AUTHORIZED
The required account or integration permissions have been granted.

EXECUTED
The operation was actually performed.

VERIFIED
The operation succeeded and evidence confirms the result.

BLOCKED
A dependency or authorization prevents execution.

Do not treat these statuses as interchangeable.

---

16. Change Management

For significant changes:

1. Understand the objective.
2. Inspect the current state.
3. Identify risks.
4. Determine dependencies.
5. Implement the smallest suitable change.
6. Validate.
7. Record evidence.
8. Report the outcome.
9. Obtain required approval before production implementation.

Technology reports should clearly communicate:

- What was changed

«Do not fabricate technical results.»

«Do not bypass security controls.»
